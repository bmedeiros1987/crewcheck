## Private channel reader

`server/financial-channel-read.mjs` is a server-internal, dependency-injected preparation module. It is not imported by Telegram or any runtime route. It accepts only private Telegram transport context, reuses the existing linked-profile resolver contract, and separately requires existing account authority. Linked profile email alone never becomes an authenticated financial identity. Owner must be active and match the resolved profile. Binding identity hashes the owner, private conversation, linkedAt and existing access-key hash; no secret is exposed or generated. Relink invalidates old consent. Group/supergroup/channel, visitor, unlinked or mismatched owner fail before financial source access.

Consent is an explicit versioned server-owned record scoped to owner, channel, conversation and exact binding: `version:1`, positive `revision`, `state:'granted'`, `scope:'financial_forecast_on_request'`, `delivery:'private_text'`, `allowModels:false`, `allowAutomatic:false`, selected categories, `grantedAt` and `expiresAt`. No default consent exists; revocation, expiry, scope mismatch and changed revision discard monetary output. The reader never creates or stores consent. Supplying these structures from a chat prompt or browser request is forbidden. An explicit owner-authenticated confirmation/management UI and durable store are separate prerequisites.

The source adapter must return `source:'persisted_financial_ledger'`, ownerId, original persisted `records` and `freshness` entries bound to exact id/revision: `{id,revision,sourceAsOf,recordedAt}`. The reader reuses `queryUpcomingFinancialForecast`, not rates/FX/roster inference. `sourceAsOf` means a trusted source observation, not SQL insertion time or now(). Future timestamps, duplicates, wrong revision and observations older than an explicitly configured maximum block all values. No production age policy is chosen here; missing policy means unavailable, and the implementation bounds any future policy to at most 24 hours. The timestamp does not prove a bank settlement. Empty/partial selections retain unknown coverage; no_data never means zero or an empty ledger.

After async source access, the reader re-resolves binding and consent, checks time again and requires a synchronous host-owned `isCurrent({ownerId,binding,consentRevision})` lifecycle fence immediately before returning. A missing fence means unavailable. A real adapter must fence distributed revocation/account changes, not return a constant. The result is read data, not a send permit: a future transport must revalidate against durable current authority immediately before separately authorized delivery and discard stale queued responses. No transport is implemented in this draft. Internal ids, source/rule references, account identity, evidence documents and link hashes are stripped from the prospective channel result. No data is forwarded to an external model.

## Production state and migrations still required

The existing ledger migration `migrations/20261017_020_financial_ledger_mysql.sql` and gate are unchanged and are not executed/inspected on production. `createFinancialSqlStore.list()` currently returns records, not trusted source observation freshness. Its `created_at` is storage time and is deliberately not repurposed as source freshness. The current profile resolver also does not expose all persisted link-generation fields to the menu. Therefore **this module has no usable production adapter today**. Tests do not establish a real account, source availability, binding or consent.

Before activation, a reviewed implementation must: (1) extend the existing trusted capture producer and immutable snapshot JSON to preserve source observation provenance per revision, leaving old records unknown rather than backfilling; (2) provide an account-bound persistent consent/revocation store with optimistic revision, expiry and exact binding scope; (3) cover consent in account erasure/relink/revocation and the existing auth lifecycle; (4) expose the persisted linkedAt/generation only through the existing verified private resolver; (5) enforce the delivery-time fence and protect against queued responses after revocation. Prefer existing storage mechanisms only if access/deletion/revision guarantees are demonstrated. If a separate consent table is needed, its additive migration must be independently reviewed and manually authorized before execution. No consent table/migration or write executor is added here. No credentials, permissions, costs, outbound messages or operational gates are requested by this draft.
