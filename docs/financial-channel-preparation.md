## Read and consent boundary

`server/financial-channel-read.mjs` remains the shared channel policy. It accepts only a private Telegram transport context, independently verifies the owner and requires exact binding-scoped consent: `version:1`, positive revision, granted state, `financial_forecast_on_request`, `private_text`, `allowModels:false`, `allowAutomatic:false`, chosen categories, grantedAt and expiry. Missing consent never defaults to granted. Binding hashes the owner, conversation, persisted linkedAt and existing access-key hash; relink invalidates prior consent. A profile email or request field is not authority.

The source is the canonical persisted ledger, with freshness evidence tied to exact record id/revision/fingerprint. `sourceAsOf` means a verified source observation; SQL created_at, import time and read time do not establish it. Missing/future/old/duplicate evidence fails closed. Source-age policy must be explicitly configured (at most 24 hours); no production age policy is chosen. Latest-revision validation, settlement distinction, original money/currency, partial states and null versus zero reuse the existing reader. Internal source/evidence/owner/link identifiers are stripped from the prospective channel result.

The policy revalidates owner/binding/consent after asynchronous reads, checks expiry after the final await and requires a synchronous lifecycle fence before returning. The SQL composition implements this boundary using durable locks. A returned read is not a send permit: a future separately authorized delivery must revalidate current authority before sending; no sender is included here.

## Concrete SQL continuation (2026-10-20)

`server/financial-channel-sql.mjs` now implements the adapters against the existing MySQL adapter, platform profiles, bidirectional `crewcheck_telegram_state` links and canonical persisted revisions. It has no runtime import or HTTP/bot route. It does not depend on a browser-local financial snapshot. Its methods are callable only by a future separately reviewed existing authenticated host; test injection is no longer the only implementation.

- `previewConsent` resolves both durable link directions and the owner profile, returning the exact current binding and consent revision. A chat/request email is never authority. `changeConsent` requires the existing authenticated owner identity, explicit confirmation of this binding, selected categories, an expiry and expected revision; revocation is durable and remains possible after unlink. Concurrent grants/revocations serialize with the profile and consent locks. A stale revision cannot silently overwrite a later revocation.
- `recordSourceObservation` stores immutable published-source observation evidence against an existing owner/entry/revision/fingerprint; mismatches, future timestamps and attempts to change an earlier proof fail. `captureTrustedSource` composes the existing reviewed forecast producer and this observation writer, with unchanged amounts and calculation rules. It validates observation evidence before capture; interrupted batches/retries reuse canonical idempotency, and any record without its matching evidence stays unknown. This is only for a trusted source ingestion host after verification of the actual published timestamp, not a way for the browser or Telegram to assert arbitrary freshness. The current HTTP capture route remains unchanged and cannot supply these observations. Existing observations are never refreshed merely by replaying a capture.
- `read` executes the prepared reader using the durable links, profile, consent and a single joined record/observation query. Transactions explicitly select READ COMMITTED for that transaction only, before BEGIN. This fixes the independently reproduced old-snapshot race when the reader waits for a canonical writer's owner lock. All financial writers and account erasure share the owner-profile first lock. The selected record revision and its freshness come from the same query; a new revision never inherits old proof. Revocation/read ordering is linearized under real InnoDB locks, and time expiry is checked again after commit. A returned snapshot is still not a send permit: later queued delivery would require renewed authority verification.
- The existing full-account erasure statement helper includes both prepared tables, under its existing transaction and missing-table guard. Roster replacement remains unrelated and cannot delete financial history or consent. The optional-table cleanup therefore remains safe before this manual migration exists.

### Prepared migration, impact and rollback gate

`migrations/20261020_021_financial_channel_preparation_mysql.sql` creates two additive InnoDB tables, for versioned private-channel consent and immutable per-revision source observations. There is no DDL in startup/deploy, no backfill, alteration of financial revisions, FK to rosters, default grant, new DB privilege or flag activation. Existing records have unknown source freshness until actually verified. No migration or production schema was inspected/executed. A future production operation requires separate authorization of this exact migration and its target; code presence is not migration approval.

Inactive rollback was rehearsed only on the new empty/synthetic tables: remove channel composition first, then drop only these two prepared tables. Canonical ledger revisions remain untouched. Reapplying the migration creates empty consent/evidence tables and grants nothing. For any later active deployment, revoke/disable channel delivery and quiesce readers/writers before schema rollback; do not drop a table while consumers rely on it. No rollback command was run against production.

It accepts no production DB URL/host/password and asserts the dedicated schema/server. The container/socket/data are removed in finally. Local and independent review passed 17 groups covering schema replay/missing schema, grant concurrency, durable revocation, current-revision freshness, capture/replay, old snapshots while waiting on owner locks, erasure/read races, slow-commit expiry, transaction rollback, expiry, null/zero and inactive schema rollback.
