# Finite promotional beta admission — OFF integration

This stacks on the existing shared-credit candidate, not a second ledger. No public caller mode, environment reader, service registration, grant, real balance, entitlement, payment, schema migration or provider call is added. `CONCIERGE_PROMOTIONAL_BETA_SHIPPING=false`. The existing caller still rejects modes other than the reviewed pilots. Neither those approvals nor their consumed counters are reused.

A first subsidized beta can be independent of Asaas: a future explicitly approved promotional grant is a separate idempotent source of credit, not a subscription or payment assertion. Missing balance denies. Account identity must be the SHA256 of the authenticated canonical public account ID, verified again by the trusted resolver and sealed job binding. It is never derived from phone alone. The grant path and its authorization do not exist in this patch.

The adapter conforms to the existing `admission.allows/reserve` capability. It is injected into the existing sealed production store in tests. The existing receiver verifies raw HMAC before enqueue; store link/profile locks and freshness checks remain; the same transaction reserves global/account credit plus a finite promotional reply count and the preparing marker before any engine effect. A stable approval manifest binds account/sender/recipient/period/quantity/program/global cap. Editing the same approval cannot reset its counter. No automatically generated approval IDs, manual15-minute renewals per question or rollover grants exist. An approved finite period can be up to31days; this code bound is not approval for a real period.

The dispatch test uses the actual HMAC receiver, AEAD store and transaction/lifecycle logic with a mysql-shaped serializable fixture. The separate MySQL suite verifies the adapter against real InnoDB and a real server stop/start, including one remaining reservation. Engine/transport in these tests are synthetic. This does not establish a deployed quote resolver, production canonical lookup implementation, arbitrary-question read-only engine, approved host configuration or distributed revocation beyond the existing store.

Minimum executable path before activation:
1. Review this adapter and #1249, including independent review and exact CI.
2. Implement/review a one-time promotional grant keyed by an explicit approval, canonical account and period, with bounded immutable amount; no automatic seed/refill, Asaas dependency or real grant in tests. Select the single fixed global budget program so a new program ID cannot evade total spending.
3. Wire a trusted quote/current-binding and budget reconciliation resolver in the existing caller; preserve the current raw-HMAC ingress, confirmed owner/consent, sender/baseURL allowlists, read-only canonical engine scope, lifecycle and no-retry behavior. A new explicit reviewed restricted mode is required; do not use the pilot mode to activate this adapter.
4. Obtain specific approval for account/audience, promotional amount, total replies, start/end, reserve price and global expenditure margin, then grant/configure only that scope. No voice activation. The existing quoted service window and all fees must be accounted for; US$20 is an app-controlled shared monthly budget, not proof of a provider invoice hard cap.

Proposal to decide, not implemented or approved: one Bruno account, fixed nonrenewing promotional balance and response count over a defined trial period, WhatsApp TEXT only, no outbound initiation, no voice/AI, no payment subscription. Values should be chosen from current quote/obligations, not from the historical voice average or assumed-free inbound traffic. The adapter accepts only explicit finite approved values; changing channel does not mint balance. Uncertain reservations remain consumed until an independently reviewed reconciliation proves otherwise.

Expiry is rechecked after awaited credit writes (throw/rollback) and the shared store also rechecks the existing admission immediately before invoking the engine after preparation COMMIT and link lookup. If expiry occurs after a successful commit, the reservation is retained, engine/send do not start and the engine-active fence clears through the existing finally path. This small shared-store guard applies to existing admissions too; no authentication, transport or quota contract is relaxed.
