# Telegram free admission candidate OFF

This is an isolated review candidate over main `a9ead88276a34bd625412e4653127ab6619c42f3`, not an activated performance policy. Three new files are proposed: `server/telegram-free-admission-off.mjs`, `scripts/regression-telegram-free-admission-off.mjs` and this document, plus narrow path/test/evidence additions to the existing `.github/workflows/telegram-concierge-menu.yml` offline job. No production import, route, generator, environment variable, database write, provider, queue, timer, medical flag or paid-message capability is changed. `TELEGRAM_FREE_ADMISSION_SHIPPING=false`; only synthetic tests explicitly instantiate it enabled.

## Exact bounds

- One in-flight ordinary free read per canonical owner, shared across the owner's already-authorized delegates and link revisions.
- Three admissions in any sliding10-second window and six in any sliding60-second window; denied attempts do not debit a window. At the exact expiry boundary, an old timestamp no longer counts. No daily/monthly allowance.
- At most2,000 owner entries and six timestamps per entry. Prune expired idle windows; never evict a live window or an in-flight operation. Capacity refusal does not create another owner entry.
- At most two free reads in flight per capability. A future host MUST create exactly one shared instance per Node process for all eligible ingress paths; creating one per request/route would defeat that aggregate bound. Separate Node processes have separate state. Restart resets this ephemeral protection. It is not cross-instance or durable enforcement.
- No wait queue or automatic retry. Cooldown retry-after is computed from both violated windows. Busy/capacity returns a one-second retry suggestion, not a prediction that the operation will finish then.
- Busy/cooldown notices are eligible at most once per owner per10 seconds, with an additional aggregate ceiling of three notices per sliding10-second window across all owners. Denials for unknown owners at global/capacity saturation share a single process/capability notice clock, so new IDs cannot allocate denial state. The helper never sends a notice.
- An actual read completion or rejection releases its slot in finally. An external timeout does not release a still-running underlying operation. There is no Promise.race deadline, auto-refund or silent retry. Existing network/SQL cancellation owners remain unchanged.

These starting bounds are conservative policy choices, not measured throughput or availability guarantees. The actual SQL pools, provider quotas and scheduled-notification dispatcher remain independent and authoritative.

## Internal authority contract

`run(authority, operation)` is not a public endpoint. The trusted host must construct authority from the existing authenticated account/private-chat binding or existing visitor grant. Never pass request JSON, a Telegram-supplied owner/email/plan, or arbitrary model output as this argument.

The host supplies `channel:'telegram'`, `lane:'ordinary-read'`, `authorized:true`, canonical `owner.email` and `owner.publicId`, separate `actor.kind` (`owner` or `visitor`) and `actor.id`, and a synchronous `isCurrent` predicate closed over the original authenticated session, actual private chat, actor, link/owner/visitor revision and current ACL. That predicate must test the captured authority, not merely return a request flag. It is checked before admission and after the read. A revoked result is suppressed and has no value field. Async predicates are refused and their possible rejection is consumed, without waiting or invoking the producer. Read operation effects cannot be undone; therefore the operation must not include the sender or medical handler.

The limiter's owner key excludes actor and link revision deliberately: changing a delegate or relinking cannot mint a new quota for the same owner. Authorization, private response routing and data selection must still use the actor/grant; the limiter grants none. Guest Basic2 (one family member plus one colleague) and visitor ACLs belong to their existing owner and are not changed here. No response cache exists, so nothing is reused across accounts, actors or health contexts.

## Canonical plan resolution and evidence

The helper imports only the existing pure `resolvePlatformEntitlement` from `server/platform-entitlement.mjs`; it does not copy plan regexes or subscription/billing calculations. Its `entitlement` evidence, when already available to the trusted host, contains canonical profile, subscription and server `observedAt` wall time. A paid exemption requires matching owner email/public ID, matching subscription owner when present, and age strictly below30 seconds, never future-dated. Canonical subscription expiry is evaluated at the current wall time. This module does not enable legacy-profile trust.

Missing, stale, mismatched or malformed evidence is treated as free. A wall-clock high-water mark prevents rollback from resurrecting expired paid evidence; monotonic admission-clock rollback, invalid or unsafe numeric magnitude refuses admission without clearing windows. Missing authenticated authority is rejected, not converted into a free account. A generic client `plan`, actor's own plan or cached paid badge cannot grant a paid exemption. No evidence cache or SQL query is introduced. The integration owner must identify an already-authoritative bounded-age context or pass no evidence and use conservative free treatment. Current user/role revocation must remain enforced by the host even during this maximum evidence age; this is not a replacement entitlement service. Paid reads retain existing authorization and are not newly granted or billed here.

## Medical safety boundary

There is no keyword-based medical bypass. The helper does not parse message text or callback data. It refuses non-ordinary lanes without executing work; consequently **medical requests must never be sent through it by the future host**. Their current canonical handler must remain on its own authenticated path, unaffected by ordinary exhaustion or helper capacity.

The existing auxiliary emergency router also handles pharmacy, hospital, hotel, health-plan and location operations (`server/v1391/emergency.mjs:918-977` at the inspected baseline). Bypassing all of that router, every `cc_emergency` string, or arbitrary text containing “emergência” would be too broad. Preserve the exact authorized medical draft/confirmation/help/closure lifecycle, its correlated location intent, recipient checks, consent, expiry and existing cooldown. Do not invoke the whole effectful handler merely to classify a lane. Ordinary exhaustion must not block authorized medical confirmation, help, closure or cancellation. OFF coordination work #1241, paid WhatsApp/voice and recipients remain unchanged. Telegram acceptance does not guarantee receipt or help arrival.
