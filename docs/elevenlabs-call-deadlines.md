# Private wakeup voice deadlines (code only)

No credentials, provider configuration, real account records, voice calls or channel activation are changed. Ownership was checked against open PRs: #1217 owns only its operational import/scheduler/consent route and is preserved; #872 changes UI components, not this transport. This patch uses the existing private module and existing queue.

Each private HTTP phase has its own fixed maximum covering headers and body: ElevenLabs synthesis 18 seconds, Infobip upload 15 seconds, call creation 15 seconds, play/hangup 10 seconds each. Redirects are rejected; there are no automatic retries. Test injection may shorten a deadline, never increase it. Audio is read as a bounded stream (4 MiB); JSON/action responses are limited to 64 KiB. The existing prepared voice-settings transformation is preserved.

A timeout aborts the request, bounds the caller's wait and produces an uncertain outcome. It does not prove that the remote provider stopped or that no charge/call occurred. If a dependency ignores abort, a late response cannot advance to another phase or register a late call job. Manual and scheduled wrappers both stop on a configured private attempt; they cannot fall through into another native TTS call. A genuinely unconfigured private path keeps its previous native selection behavior.

Callback action claims are set before I/O. Concurrent or replayed play/hangup events do not create a second action within this process. Unknown/finished call IDs do nothing. This is not durable cross-process callback deduplication: the existing call-job map and its 30-minute TTL remain process-local. A lost creation ACK can leave an unknown remote call, and a timeout cannot retract a completed remote action. Reconciliation, production ingress authentication and real recipient delivery are not established by these offline tests. Scheduled-phone guards remain closed.

## Existing Telegram requirements and remaining work

This is a source inventory, not a read of Bruno's live linkage, plan, quota or provider account:

- `handleTelegramLinkStart` and the existing bot `/start cc_…` handshake create the account/email-to-chat link; the scheduler reads `link-email:<email>` from `crewcheck_telegram_state`. The user must start the CrewCheck bot from the authenticated app link if not already linked. No agent-generated link or real message was sent here.
- The existing username helper accepts a normalized cached username first; only when absent does it obtain `getChat` data for the linked chat. This is not a fresh check that a cached public username still belongs to that recipient. A public Telegram username is needed for CallMeBot. Its current existence/ownership was not checked against a real account. The status GET can refresh/persist missing username/cache data, so it was not used as a SELECT-only preflight.
- `/api/telegram/callmebot/authorize` records an authorization-request timestamp and sends the linked user the CallMeBot bot link. The user must personally open that bot and choose Start. This endpoint writes state and sends a message; it is not a read-only preflight and was not invoked.
- `/api/telegram/callmebot/verify` makes a real test call. On acceptance it stores onboarding version 2 and `callMeBotVerifiedAt`. A legacy shortcut (username + linkedAt without onboarding version) may also mark displayed readiness; neither a legacy flag nor HTTP acceptance proves fresh voice consent or an answered call. No verifier was invoked. Voice test authorization is separate from the approved single WhatsApp test.
- `consumePlatformUsage` already reads the subscription/plan and timezone month, uses a transaction for its monthly counter, and has an admin exemption. The onboarding verifier refunds on any non-ok result. These are existing manual-test semantics, not a per-job reservation: scheduler crash/re-entry and uncertain results need a durable job-key admission and must not refund an ambiguous paid attempt. No plan, quota or permission was changed.
- The app deliberately keeps `telegram-call` unavailable pending linked recipient, franchise and authorization; `phone_binding_unavailable` independently blocks scheduled phone jobs. Connecting the HTTP transport alone cannot open either guard. A reviewed capability must bind current account ownership, channel proof/consent and durable admission before enabling the selector/dispatch path. Existing legacy email-key linkage must not be silently treated as a new account-generation voice proof.

When the user is awake, the minimal personal actions are to confirm the existing canonical Telegram link/public username (or complete its own `/start` flow), authorize CallMeBot personally if absent, and separately authorize any real voice verification/cost. No action is requested now. Technical durable admission and current-owner/consent capability are still code blockers; they are not solved by asking the user to flip a flag or buy a plan.

## Offline validation

`regression-elevenlabs-call-deadlines.mjs` runs raw/prepared with fake fetch and synthetic identifiers. It covers stalled headers/bodies, abort-ignoring transport and late ACK, bounded response sizes, concurrent/replayed callbacks, plus real prepared manual/scheduler wrappers with zero native fallback after a private timeout. Existing v14405, wakeup delivery and v14408 voice-policy regressions must continue to pass. No live network, database, permission prompt, paid call or physical phone receipt is involved.
