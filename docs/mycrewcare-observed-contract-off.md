## Prepared same-session coordinator

`createMyCrewCareObservedCoordinator` accepts an injected trusted acquisition boundary only; no default provider/native/browser implementation exists. A binding copies account/session/profile identifiers into immutable memory. Each read creates one unique request/generation and AbortSignal, acquires fresh profile-before, cards, every linked detail, then profile-after. Every page must return matching account/session/request metadata. The coordinator clones each DOM on arrival so later caller mutations cannot rewrite captured observations. Only after all joins and both identities pass can one immutable, non-importable observation be published.

Bind, cancel, disconnect and a newer read invalidate the generation and abort pending work. Late completion cannot publish or clear the new generation. Account switch tests cover all four acquisition stages. Identifiers are not persisted or logged. Global/tenant uniqueness and immutable real identity, authenticity of injected metadata, native same-session acquisition and a bounded real acquisition timeout remain unproven/unimplemented. This component prepares lifecycle mechanics only; it does not grant authentication or activation. Both release constants remain false.

CI now filters observed decoder/coordinator, fixtures and suites; jsdom22.1.0 is isolated under RUNNER_TEMP, with scripts disabled. Both observed suites execute in each of the three zones before/after preparation. Empty required values fail; nonempty unknown confirmation is preserved. The ownership allowlist adds only the two exact coordinator paths beyond the previously reviewed decoder slice.

Reentrant abort listeners are treated as newer invocations: each transition reserves its token, detaches the old pending controller, clears only its own previous observation and installs its binding before firing abort. A read superseded synchronously by that callback exits before starting acquisition. Finally clears pending only by controller identity, never by an assumed live generation. Tests exercise nested read completion order and nested cancel/disconnect/bind; a later explicit cancel must reach the nested controller.

## Prepared isolated WebView source (OFF, no caller)

`CrewCheckMyCrewCareObservedWebViewSource` now implements the existing `ObservedSource`; it does not add another coordinator, page decoder, authentication flow or operational importer. Its explicit `prepare` factory uses `CrewCheckMyCrewCareProfile.create` for one captured account and reads the packaged generated asset. No Runtime/Home/MainActivity invokes that factory. The existing release/UI gates remain false, and the panel remains unmounted. The factory itself does not allocate a WebView or navigate; allocation is deferred to an accepted acquisition on the main looper. Unsupported isolated profiles fail closed with no fallback.

One source instance belongs to one account/session/request and the generation assigned by `ObservedAcquisition` on its first request. Cancellation for any different account, session, request, generation or expected profile identity does not close it. Every navigation target is constructed from the current phase; detail IDs are conservatively limited to digits. HTTPS host, port, exact case-sensitive path/query, absent userinfo/fragment and native `getUrl()` are checked before evaluation and again after the result. Unexpected redirects/navigation, main-frame HTTP/SSL/load failures, downloads and renderer loss fail closed. A finished event without a matching start fails; duplicate finished/value callbacks and callbacks after cancellation/replacement do not advance the owner.

Each page request creates a distinct WebView in the **same existing account profile**, destroying the prior view first; callbacks also check the exact view instance. This prevents late same-URL events from being attributed to the current page without constructing another profile or authentication flow. Cookie/session continuity across these views is not presumed; it must be checked in the separately authorized physical test. The native driver creates, navigates, evaluates, queries and destroys the WebView only on the main looper. Posting always defers; it never waits for the UI thread. Dispatch and cancellation share the source ownership monitor, while delivery enters the acquisition owner without holding the source monitor to avoid lock inversion. On main, cancel stops/destroys immediately before profile cleanup can execute inline. On a worker, stop is enqueued before Runtime enqueues cleanup on that same main looper. Cleanup epochs/barriers remain authoritative in the existing owner. The source does not clear global cookies/cache or mutate the profile factory/store. It denies permission requests, popups, file/content access and mixed content. Provider scripts are disabled during navigation and all subresources/subframes are blocked; JavaScript is enabled only for the generated extraction. This intentionally supports only server-rendered observed DOM; no assumption is made that this suffices on a real device/provider.

The wire reader accepts only a JSON-string-wrapped envelope from `evaluateJavascript`, <=2MiB callback and <=256KiB decoded payload, strict JSON with duplicate keys/type coercion/invalid Unicode/extra metadata rejected. Row count is bounded to50, field count to14 and field values to240 characters by the acquisition's **same** typed-page validator, now reused at the source receipt boundary. This parser only handles the bounded wire representation; it does not reimplement DOM extraction or business identity. No HTML/cookies/hidden state/credentials are returned or logged. Requests are serialized as data, including quote/backslash escaping; profile/cards/detail scripts produced by the native driver execute against the reviewed synthetic DOM in the Node fixture.

Validation:241 source cases in the actual Java class plus the existing68 acquisition cases. The matrix covers4 phases ×4 queue/navigation/evaluation/receipt boundaries ×cancel/cleanup/timeout/switch; malformed origin/navigation/wire payload; delayed/duplicate events; A cleanup preserving B; foreign cancellation; worker/main cleanup ordering; SSL/HTTP/renderer/download/POST failure; unsupported profiles; and deterministic concurrent source dispatch vs cleanup using latches/thread blocking without random sleeps. Eight native-produced evaluation scripts are executed with the actual asset and synthetic DOM, including quoted/backslashed account/session/request metadata. Android/profile/store stubs model scheduling and prohibit off-main WebView calls. They prove the Java control flow and serialization, **not** physical WebView/network behavior. Android SDK compilation is a separate CI gate.

Platform limitation: Android documents that `shouldInterceptRequest` sees only the initial URL of a redirected resource; `shouldOverrideUrlLoading` does not cover app-initiated loads or POST. Explicit loads are validated before dispatch, observed redirects are denied and native URL is revalidated before/after extraction, but this is not a proven network egress firewall. See [WebViewClient reference](https://developer.android.com/reference/android/webkit/WebViewClient) and [WebView threading reference](https://developer.android.com/reference/android/webkit/WebView). Existing service-worker/profile behavior and cookie cleanup on a real device require separately authorized physical validation before any activation. There is no real session or provider call in this candidate's validation.
