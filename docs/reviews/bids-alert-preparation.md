# BIDS preferences and delivery boundary

This change provides an account-isolated, explicit opt-in panel inside BIDS. Auto and Manual preserve the user's time; quiet hours apply to both. Todos selects all channels without overwriting individual selections. CrewCheck is the product label for native and installed browser use. Selection is not permission, pairing, transport readiness, scheduling, delivery or receipt.

The current campaign registry is null and eligibility is unverified. The reported opening on 11 November 2026 at midnight is not configured as official data. Current communiqué, official timezone, target month, closing and eligible audience remain required. Existing yearless reference dates remain references, with copying disabled. No producer, provider or paid channel is activated by saving preferences.

The pure planner handles verified owner-bound roster intervals, explicit offset dates, quiet hours, source revision and one declaration per campaign context. The live endpoint has no verified roster adapter; Auto therefore cannot currently claim to follow the user's actual roster or infer rest. Already-did is a personal declaration, not proof of submission to the airline; it does not cancel independent manual-window alerts. GET performs no write. Mutations lock the current account binding, use revision comparison and request idempotency. Account deletion includes the new namespace.

## Required work for actual delivery outside the app

The current service worker only handles cache/update/fetch. There is no PushManager subscription, account-bound subscription registry, Web Push sender, push handler or notificationclick handler. Browser permission alone cannot deliver this campaign with the page closed.

1. Add an authenticated subscription registry bound to the current canonical public account ID, installation ID and consent revision. Validate endpoint/key structure and allowed HTTPS push-service origins; encrypt sensitive subscription material at rest. Bind changes under transaction, reject stale account identities and delete/revoke subscriptions on logout, account deletion, explicit opt-out and installation reassignment. Do not log endpoints or keys.
2. Add explicit contextual device activation after a user tap, secure-context and support checks. Register the worker and call PushManager.subscribe only after permission is granted. Display unsupported/blocked/unknown states honestly. On iOS/iPadOS, installation on the Home Screen and a user gesture are required; never imply that selecting CrewCheck grants permission.
3. Add a provider adapter using a dedicated VAPID public/private key pair and contact subject. Keys have NOT been generated, configured or requested in this change. Confirm authorization before creating/setting server secrets or exposing the public key. Existing endpoint TLS may be reused; confirm configured HTTPS origin, worker scope and deployment behavior.
4. Add an inert-by-default transactional outbox keyed by account, verified campaign context, installation and channel. Recheck source, eligibility, consent, current ownership, quiet period and deadline before claiming and sending. Reject duplicate claims; preserve uncertain attempts without automatic replay. Expired subscriptions (404/410) become inactive. Provider acceptance is not device receipt. Retry only definite pre-send/transient failures under bounded policy.
5. Implement worker push and click handlers with minimal payload, owner/installation epoch checks, source/context dedup and a single notification tag. Keep account-private details out of lock-screen text. Click must open an authenticated in-product route, without changing BIDS status. Revocation races and closed-app delivery need real-device tests.
6. Add authenticated, installation-bound receipt reporting for worker processing/display attempts and explicit user acknowledgement, each idempotent and separate. A worker/display acknowledgement must not be labeled as user-read or guaranteed delivery. Permission revocation, offline delivery, expiry, logout, account switching, retries and source changes require integration tests.
7. Native Android scheduled alarms need an owner-bound cancellation/revocation contract before reuse. Relógio requires verified pairing, permission, a BIDS producer and installed native/Wear validation. CrewCierge requires verified two-way account/recipient binding, per-campaign consent and confirmed transport configuration. None is inferred from the channel checkbox.

Missing authorization/configuration: approval to generate/configure dedicated VAPID key material and contact subject; verified production HTTPS origin/scope; each device's explicit permission/installation consent; official BIDS source and audience resolution; approved transport activation after independent review. No new grants, secrets, sends or costs are introduced here. Web Push remains an open task.

Primary references: [MDN PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe), [WebKit Web Push for iOS/iPadOS web apps](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

## Validation limits

Policy, authenticated API isolation/CAS/idempotency and real isolated MySQL regressions cover the server boundary. Browser tests render the real component/styles, verify dark/light, 200% text, narrow widths and shortened viewport with fixed-navigation bounds. The navigation is a harness, not a physical-device keyboard or full shipping-app test. No real notifications or provider calls are made.
