# Manual gate and subsequent source updates

Base: published #1141, `49645f4b7b7df7eed59a1566d6626c51b5b47cc2`.

The existing account/flight/date/route manual entry remains authoritative. Source queries keep their existing cadence and never write the manual store. An explicit local choice can keep the manual gate or accept a proven later source gate. The decision survives reload; accepting retains the manually entered terminal. Labels include UTC timestamps, avoiding dependence on the device timezone.

Only an explicit departure-gate update time can establish a later change. HTTP receipt, browser cache time, aircraft signals and generic provider `updated` fields cannot. In particular AirLabs documents `updated` as the last aircraft signal: https://airlabs.co/docs/flight . No currently configured provider is assumed to supply a trustworthy gate-update time.

The existing custom-source data contract may opt in with `departureGateUpdate.schema = crewcheck.departure-gate-update.v1` and matching primitive-string gate, flight, origin, destination, scheduledDepartureUtc and updatedAt (absolute ISO timestamp with timezone). The server validates these against the source payload's own identity, never request defaults. The public projection passes a normalized version/kind/provider proof. This does not configure or activate any source, including Cirium, or authorize a paid query. Without this proof, divergence remains visible and manual stays; the UI cannot offer an unproven “new change”. Production coverage of this optional contract is unverified.

The client rechecks proof, occurrence and freshness before display and each explicit write; stale rendered choices, changed account/token, changed source/manual revision and replays fail closed. A retained user record without a token cannot accept/keep. This is a local continuity fence, not a replacement for server authentication. Manual values are neither uploaded nor synchronized by this change.

Out-of-order or missing-proof responses retain only the latest still-fresh proven gate/proof and its original receipt anchor. Status, operational times, aircraft, terminal and the query receipt continue updating from each incoming response. Equal source timestamps with different gates persist ambiguity until a later source timestamp. Refresh cannot extend proof validity. Presentation receipts suppress repeat sound/system notices while allowing reconstruction of an unhandled Pulse. Later timestamps, including a return to a previously seen gate, remain distinct. Home reconciles notices to the current candidate; the shared hook re-reads current storage before removing obsolete notices after a manual/cache/account change.

Validation uses synthetic storage, times and flight IDs only. Unit fixtures cover three timezones, invalid/absent/future source clocks, offset equivalence, identity, watermark, persistence, replay, account scope, failed writes and offline expiry. Browser fixtures bundle actual Home cache/notice functions and real React card/editor, block external requests, and exercise keep/accept/reload/dedupe/late responses/stale source/session/account. Existing polling, source identity and prepared-materializer regressions remain required. No real user data, Telegram messages, webhook/token/service changes, native release or paid provider queries are part of this change.
