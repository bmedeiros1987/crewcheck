# Telegram binding transfer — isolated protocol candidate

Base f5d041ae. Work is the only writer. The current prepared handlers reproduce two account forwards for one chat after relinking; a warm local cache can choose A while the persisted reverse index chooses B. Relinking A again leaves B's forward. This is a demonstrated synthetic mechanism, not proof of which real account was linked by the user or of actual disclosure.

This first candidate implements the transaction protocol and cache adapter only. **It is not wired to the running routes or senders. The old production mechanism remains unchanged and real transfer remains blocked.** No migration, real lookup, linking command, message, account mutation or production database operation was executed.

The protocol uses the existing MySQL JSON-state table. A transaction locks one fixed mutex row before reading or modifying pending/forward/reverse/code records. No DDL is in the production module. One current challenge per target account; newly issued challenges expire after10 minutes; legacy challenges without expiry are refused. Private chat/from identity is required. A replacement needs a second explicit confirmation bound to the same chat and unchanged source revision. The later app adapter must expose that confirmation clearly instead of silently replacing an existing association.

Confirmed replacement removes superseded generations and aliases atomically and creates one forward/reverse/code generation. Changing account back uses a fresh challenge, not an old code. Same healthy pair is idempotent and preserves its generation/CallMeBot metadata. Incoming transient chat snapshots are not moved by this protocol. A transfer does not inherit another account's CallMeBot authorization.

Readers verify both indices, uniqueness and relevant metadata; orphan or conflicting legacy states fail closed. Local cache is never binding authority. Metadata updates use identity/generation plus metadata CAS, preventing a late username/CallMeBot response from recreating a revoked pair or overwriting a newer update. Commit/rollback uncertainty destroys the connection, never returns a success result and does not retry a consume automatically. The authoritative state must be read before resolving an uncertain result.

Replacement deliberately requires an admission callback: until every sender and queued/in-flight work is handled, there is no safe real transfer. This draft does not cancel alarms to make a test pass. Already accepted Telegram messages cannot be recalled by a database rollback. Still required: integrate all route readers/writers, callback confirmation, account deletion, password recovery, alarms, notification queues, monitor and visitor-owner notices; validate admission at send time and exact revision/source. Preserve unrelated visitor namespaces and official weather/wakeup functionality. Mixed rollout with old writers is not safe merely because this module has a mutex.

The bounded operator diagnostic is not an HTTP endpoint. It requires the two exact known accounts and executes a read-only consistent snapshot; output is only labels, whether both point to one chat and index-consistency booleans. No address, chat ID, code, hash, roster or credentials are returned. It does not attest old process-local caches. It has been tested only synthetically; no real backend access is present in this executor. Existing public status GET is not a substitute because it may persist username metadata.

Local synthetic scenarios cover normal linking, explicit transfer, fresh-challenge reversal, duplicate legacy rejection/repair, cache warm/cold agreement, stale metadata, competing challenges, expiry, case-insensitive SQL-key collision, private-chat restriction, storage failure and uncertain transaction outcomes. The same suite has a dedicated Unix-socket-only disposable MySQL factory and is added to the existing network-disabled CI container pattern, using a separate fixture database. Real InnoDB results remain pending; no local MySQL server is installed. CI/review and complete application integration are release gates, not optional follow-up.

Tester observations of linked/synchronized UI do not prove the GTest identity or uniqueness. Until a bounded authorized backend read confirms current state and the completed correction is verified, do not send a nickname, PDF or data query to the bot and do not repeat the old link operation as rollback.
