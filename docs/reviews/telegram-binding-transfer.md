# Telegram binding transfer — isolated protocol candidate

Base f5d041ae. Work is the only writer. The current prepared handlers reproduce two account forwards for one chat after relinking; a warm local cache can choose A while the persisted reverse index chooses B. Relinking A again leaves B's forward. This is a demonstrated synthetic mechanism, not proof of which real account was linked by the user or of actual disclosure.

The canonical preparer now integrates authenticated start/status handlers, confirmation callbacks, canonical readers, metadata CAS and selected sender adapters. **This is an unpublished candidate; real transfer remains blocked in its handler until all legacy queues, replies, deletion and rollout gates are closed. The production mechanism has not been changed by this work.** No migration, real lookup, linking command, message, account mutation or production database operation was executed.

The protocol uses the existing MySQL JSON-state table. A transaction locks one fixed mutex row before reading or modifying pending/forward/reverse/code records. No DDL is in the production module. One current challenge per target account; newly issued challenges expire after10 minutes; legacy challenges without expiry are refused. Private chat/from identity is required. A replacement needs a second explicit confirmation bound to the same chat and unchanged source revision. The prepared handler exposes a private inline confirmation; a confirmed replacement still refuses execution without complete delivery admission.

Confirmed replacement removes superseded generations and aliases atomically and creates one forward/reverse/code generation. Changing account back uses a fresh challenge, not an old code. Same healthy pair is idempotent and preserves its generation/CallMeBot metadata. Incoming transient chat snapshots are not moved by this protocol. A transfer does not inherit another account's CallMeBot authorization.

Readers verify both indices, uniqueness and relevant metadata; orphan or conflicting legacy states fail closed. Local cache is never binding authority. Metadata updates use identity/generation plus metadata CAS, preventing a late username/CallMeBot response from recreating a revoked pair or overwriting a newer update. Commit/rollback uncertainty destroys the connection, never returns a success result and does not retry a consume automatically. The authoritative state must be read before resolving an uncertain result.

Replacement deliberately requires an admission callback: until every sender and queued/in-flight work is handled, there is no safe real transfer. This draft does not cancel alarms to make a test pass. Already accepted Telegram messages cannot be recalled by a database rollback. Integrated paths include password recovery, scheduled text/call adapters, weather monitor, explicit alarm tests, call callbacks and visitor-owner notice. Preserve unrelated visitor namespaces and official weather/wakeup functionality. Mixed rollout with old writers is not safe merely because this module has a mutex.

The bounded operator diagnostic is not an HTTP endpoint. ## Durable delivery admission limits

Provider admission commits a reservation under the binding mutex before external submission. Transfer checks under that same mutex refuse reserved or uncertain records. Provider acceptance is not delivery/read receipt or call completion. A definitive provider rejection can close a reservation; a generic failure, lost ACK or finalization error remains uncertain and blocking. There is no automatic expiry, retry, recovery or new retention policy. Records contain account/chat association, a generation digest, status and timestamps, never content, tokens or access keys. This storage is tested only in disposable fixtures; deployment needs privacy/retention and recovery review.

Reservation IDs do not deduplicate caller retries. Legacy jobs lack generation provenance and every caller must honor uncertainty. Prepared local alarm routes refuse arbitrary Telegram destinations and preserve independent phone channels; uncertain calls are not refunded as though no call could have occurred. Remaining conversational/verification paths keep this PR in HOLD. The actual handler still has no transfer-admission callback; tests exercise the checker directly only in isolated fixtures.


## Account erasure — isolated helper, not routed

The helper owns its transaction, takes the binding mutex before the profile lock, verifies the current owner generation, and requires a same-connection cleanup callback. Active/uncertain admission refuses removal; terminal records, aliases and challenges are removed only for the selected account. Rollback and unknown commits use the existing connection-discard boundary. Its result attests binding-state erasure only, never full account deletion. Synthetic callbacks do not prove platform profile/queue erasure. Fourteen tests pass both SQL double and isolated MySQL; no real account was deleted.

The live erasure route is not wired to this helper: it currently cancels Asaas before opening its database transaction. External cancellation, atomic profile/queue cleanup, uncertain outcomes and the complete lock order must be reconciled before that adapter is implemented. Do not attach the helper after cancellation and claim the operation was all-or-nothing. Legacy caches, conversational replies and queue provenance remain HOLD.


## Reply generation — private binding present at receipt

The webhook dispatch captures an existing private-chat binding in an async-local scope. The profile reader refuses a different generation before replying or continuing as a newly linked account; a late sender needs a durable admission for the captured generation. Concurrent chats have separate scopes. Main text transport fixes chat_id after extra options and requires explicit provider ok:true; incomplete/lost ACK is uncertain. Existing prepared factual-handler regression still runs with the actual scope helper.

This does not certify public/unbound-to-bound, visitor or explicit binding flows, which remain outside that scope. Other direct callers still need verified context; nested scoped and explicitly admitted transports may reserve twice. Accepted means provider acceptance, not delivery or completed call. There is no external retry deduplication, retention/recovery policy or permission to enable transfers. Thirteen synthetic reply-scope cases cover stale reply and stale profile generations, parallel contexts, destination override, ACK ambiguity, outage and binding-flow separation.
