## Implemented code and safety boundaries

- Read-only existing-account JWT/profile authentication for status; missing/stale accounts never cause ensureProfile/INSERT. Mutations require the approved same origin. Authenticated registration/status/revocation/receipt API is /api/platform/notifications/crewcheck-installation. Revocation works by installation even after browser subscription loss and while delivery is disabled. No public enqueue endpoint exists.
- Subscription validation restricts HTTPS to supported push-service domains, rejects URL credentials/ports and validates P-256/auth keys. AES-GCM protects endpoint/key data with account/installation/revision AAD. SQL locks canonical profile and endpoint row; revisions/ownership are rechecked and protected data is cleared on revoke. Account deletion includes installations, outbox and audience proof namespaces.
- Persistent outbox commits dispatching before I/O, so crashes/ambiguous outcomes never reset to queued. Phase two rechecks current profile, installation/revision, source, consent, preference revision and deadline under locks. It holds revocation locks during the bounded provider request. Acceptance, display API resolution and client click reports remain distinct and never become guaranteed received/read. 404/410 clears the dead subscription; unknown outcomes do not auto-retry. No body, endpoint or provider error is logged.
- Standard web-push 3.6.7 adapter uses aes128gcm, VAPID, bounded TTL/timeout and a DNS lookup that rejects private/local/reserved resolved addresses. Host allowlist and no redirect/proxy configuration protect against endpoint SSRF. The library is lazily loaded only after enabled/configured and deadline checks; tests replace it with a mock and make no external requests. A deadline is rechecked after asynchronous library loading.
- The existing scheduler calls the new producer, whose disabled path performs no producer queries. Current BIDS campaign is null. A configured campaign additionally needs trusted server-only audience provenance (bids-alert-eligibility namespace), current per-account opt-in, selected CrewCheck channel and an active installation. User-supplied campaign/role/audience cannot create that proof. Source/consent/preferences/deadline are revalidated at dispatch; quiet periods are respected and no closing is invented. Auto currently uses the explicit time/quiet preference when no verified roster adapter is available; it does not claim actual rest/availability.
- Device activation appears contextually inside CrewCheck preferences only when server configuration is ready. Selection/Todos never requests permission. A user tap requests existing browser permission and authenticates the installation. Serial lifecycle mutations, generation/CAS worker binding and checks after each await prevent old activation/cleanup from restoring or erasing a newer account binding. Logout/account switch/expiration clear local binding and unsubscribe; pre-change revocation captures the current authenticated session. Offline server revocation remains explicitly unconfirmed. Cross-tab identity changes are handled.
- Shipping sw.js imports the receiver. Without explicit activation there is no subscription or local active binding. IndexedDB stores owner/installation/consent binding, generation and persistent event claims. TTL/account/binding are rechecked immediately before display. Claim state preserves expiry, cleanup is bounded and capacity is capped. Generic lock-screen copy contains no roster/account details; clicks open authenticated /app without completing BIDS. Worker reports reconcile later through the authenticated same-account API; display/click reports are not delivery/read proof. No JWT is persisted in the worker.

## Remaining blockers and concrete next steps

1. Independent review of the complete PR996 delta and terminal CI on current main. Do not activate on the basis of the earlier foundation review.
2. Owner confirms names/presence and compatibility of existing VAPID/protection/contact/origin configuration through a supported secure interface. If absent, obtain explicit authorization to generate/configure them. No tool fallback may read secret values just to check existence.
3. Validate the reviewed disabled deployment, then approve transport enablement separately. Each device still needs an explicit contextual user gesture and permission. iOS/iPadOS requires supported Home Screen installation; browser permission alone is not server setup.
4. Confirm the current official BIDS communiqué, timezone, target month, opening/closing and eligible audience, then supply the trusted campaign/audience provenance. User report 11 November midnight is not configured as official. No universal broadcast or urgency is inferred.
5. Validate closed-app/offline delivery, OS installation, permission loss, endpoint expiry, logout/account switching, revocation races and receipt wording on actual supported devices. Pure/mock/browser CI cannot prove physical delivery. Service-worker binding checks and generic text reduce risk, but there is an unavoidable boundary between the final check and the OS display call that needs physical validation.

After code review/CI, these are configuration, authoritative-data, consent and physical-validation gates; no real send/grant/key operation is performed by this task. Relógio/CrewCierge still require their own verified links/transports and are not activated by Web Push.
