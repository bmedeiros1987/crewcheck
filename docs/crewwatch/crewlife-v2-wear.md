# CrewLife v2 Wear receiver

Separate from merged PR1083; base d5afdffa. Implements the parent's agreed phone/Wear contract in crewlife-v2-contract.json. Capability is app protocol discovery only, not permission/consent or evidence of cleanup. No phone/Companion/shared-health edits, SDK, permissions, activation, source queries, signing, versions, device or store actions.

Wear accepts health values only on /crewcheck/watch/crewlife/v2 after directed reset. The reset's source node and opaque stream bind data. Only four allowlisted source metrics exist; zero is a value. The parser requires strict JSON safe integers, original envelope times and per-metric deadlines. Rendering and load never renew time. Unknown/malformed metrics become unavailable; unknown or recursive fields reject the envelope and clear values while preserving the replay fence. Scope excludes narrative, labels, heart rate and HRV.

One SharedPreferences commit clears old/current health ciphertext and persists the node/stream/revision fence before returning reset_ack/revoke_ack. AES-GCM health payload remains separate from operational and routine stores. Migration removes v1 health ciphertext only; later v1 values cannot restore it. Data always replaces the full snapshot. Persisted high water and fingerprints reject lower revisions, conflicting duplicates and replay after malformed replacement. Retired stream nonces are never pruned; at256 retired streams a new reset fails closed. Regrant after revoke needs a new stream. Revoked tombstone before directed revoke still permits a same-revision cleanup ACK; ACK types remain distinct.

Activity observes health preferences, reloads on resume and schedules local redraw at the earliest metric deadline. No health values are displayed in Activity AOD. Complications re-evaluate each metric and carry host validity ending before the earliest rendered metric expiry, including the zero-valued ring. This is not physical OLED/pairing proof.

Compatibility: old phone/new Wear is unavailable; new phone/old or offline Wear is unconfirmed and must be blocked by the phone. New/new requires reset ACK per intended node, consent and sender generation checks. This Wear patch cannot clear an old/offline watch, prove consent, inspect Samsung data or make an old phone obey v2. Phone capability discovery, owner/generation journal, pending cleanup/retries and post-async fences remain PR1085 owner responsibilities and integration gates. No v2 snapshot application ACK is emitted (optional in contract); reset/revoke ACK prove durable local cleanup, not rendering.

Evidence: 38 actual pure JVM tests initially passed locally with synthetic data. Robolectric lifecycle tests cover real DataLayer handler, AES/prefs/cache, persisted ACK ordering, migration, replay, listener, pause/resume and partial expiry. Only Keystore key and outbound MessageClient delivery are shadowed. CI/lint/build and independent review must pass on the final SHA; physical/vendor SDK validation remains pending. Shared JSON vectors are an interoperability input, not proof the phone implementation passes them.


## Receiver-issued challenge amendment

The prior journal-loss replay counterexample is retained as regression evidence. Wear now requires the agreed challenge_request -> challenge -> reset/revoke -> cleanup ACK exchange. Challenges are SecureRandom256bit values encoded as64lowercase hex characters. Exact field names/ops are recorded in crewlife-v2-contract.json. Phone treats wearChallenge as an opaque echo, not authorization or sample freshness.

One unused pending tuple binds source node, action, streamId, revision, requestId and wearChallenge. Wear commits it before emitting challenge. Exact pending request retries reuse its nonce; a new request replaces it with a new nonce, without activating a stream or erasing active values. RNG/persistence failure yields no response and no readiness. Missing/mismatched pending challenge cannot establish/reset/revoke a stream.

Reset/revoke atomically clear health ciphertext, install the replay fence, remove pending challenge and persist an applied receipt before cleanup ACK. Exact completed retry on the still-current stream may only return its recorded ACK; it cannot clear newer data, lower the fence or reactivate a different/revoked generation. Receipt survives cache expiry and store/process reconstruction. Challenge/ACK transport success is not physical rendering proof.

After journal loss there is no pending tuple, so old reset cannot authorize anything. A delayed old hello gets a different nonce; an old queued reset cannot echo it. Data from the former stream cannot bootstrap one. This closes the demonstrated receiver replay; joint phone tests must still prove current owner/consent fencing and pending state after every async callback, per-node cleanup, offline/old peer unavailability and ACK validation. Wear tests cannot establish those sender properties.

New actual pure-JVM countertests cover lost journal/old reset+data, old hello+newnonce, pending loss between challenge/reset, wrong node/action/stream/revision/request/nonce, replaced pending tuple, RNG failure, consumed nonce replay, exact duplicate after higher data and revoke/tombstone reordering. Robolectric additionally exercises commit failure before challenge and before consuming reset, recreated store retry, lost ACK after commit, encrypted cache migration and legacy replay. CI and final independent review remain gates for the new SHA. No HealthSync/SDK/device/real health/permission/store action.

A fresh challenged revoke after journal loss (no active stream) may install only a revoked fence+cleanup receipt and ACK. It never accepts values or same-stream regrant, even at a higher revision; regrant needs a new stream with fresh reset challenge. A revoke for another existing active stream is rejected. An unknown-stream DataItem tombstone cannot establish any fence. This exception makes missing-journal cleanup provable without inventing a consent/active generation.

Phone composition tombstone: generatedAtEpochMs may be integer0 exclusively for kind=revoked with metrics={} and validUntilEpochMs=0. It carries no measurement/freshness and only advances the already bound stream/revision revocation fence. Snapshots with values still require positive, nonfuture original query time. Unknown-stream DataItem tombstone remains unable to establish a stream.
