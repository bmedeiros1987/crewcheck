# Cirium primary / FlightAware fallback (production remains OFF)

## Cirium Flex (Commercial Plan) — 27 October 2026

The account's Cirium plan is the FlightStats **Commercial Plan** (Flex APIs). Sky and other Premium APIs require the Contract Plan, so `CIRIUM_SKY_PRODUCTION_ENABLED` stays `false` and the Sky path below is unchanged. The same sequencer now runs with Flex Flight Status as primary:

- **Flex only by default (28 October 2026).** FlightAware is not contracted for production (distribution to end users requires the AeroAPI Standard plan), so the FlightAware fallback is a separate, explicit permission: `RADAR_FLIGHTAWARE_FALLBACK_ENABLED` exactly `true`. Without it, also when `FLIGHTAWARE_AEROAPI_KEY` and `FLIGHTAWARE_COST_PER_CALL_USD` are configured, the Flex options carry no FlightAware guard and the sequence gets no fallback: no cache entry, reservation or call, and the paid wrapper refuses `flightaware` before the cache as a second barrier. Flex selects the sequence by itself (`sequential: true`); `flightAwareFallback` is only the permission, and paid routing never calls FlightAware outside its budget guard. The same veto holds at the FlightAware adapter itself (`providerFlightAware`), before any transport, for every entry point (HTTP, Concierge/Telegram/WhatsApp replies and the legacy race): without the exact permission FlightAware is never called, also with Flex off; with Flex on, only calls made through the budget guard (after reservation and admission) may leave. With the permission on, a call that cannot leave (no key, provider in cooldown) is refused before the cache and the ledger; an error or timeout after a real call still counts, without refund. When Flex has no usable gate, its status for the exact occurrence is kept and the gate stays empty. `fallbackAttempted` is `true` only when a fallback may have reached the provider: a fallback refused before the network (permission, budget, missing cost or ledger, revoked admission) is not reported as a query.
- **Concierge (29 October 2026).** Concierge/Telegram/WhatsApp radar replies take the same paid routing as the HTTP radar when Flex is on: the same options (`defaultCiriumRadarOptions()`), budget, cache and ledger, with a Concierge admission (current snapshot, account, query day and exact published occurrence) re-checked around each paid call. They never fall back to the unbudgeted legacy race; with Flex enabled but incomplete the reply is refused. Paid answers are read-only: shown in the reply under the Concierge's evidence rule (a gate without a source observation time stays unavailable) and never written to the Concierge snapshot. With Flex off the Concierge keeps the legacy race unchanged.
- **Order.** For the authorized published occurrence, Cirium Flex is awaited first. A valid departure gate (not empty, placeholder, position or arrival gate) on the exact flight/route/planned UTC, in a response received at most 30 min ago, is sufficient: FlightAware is not called. Otherwise, only with the permission above, at most one FlightAware call follows, with the same identity and freshness checks.
- **Identity.** One origin-scoped call `GET /flex/flightstatus/rest/v2/json/flight/status/{IATA carrier}/{number}/dep/{y}/{m}/{d}?codeType=IATA&airport={origin}`. FS carrier and airport codes are Cirium's namespace: each binds to IATA only through exactly one consistent entry of the same response appendix. A missing or contradictory appendix rejects the row; an FS code is never used as IATA. The planned departure comes only from `scheduledGateDeparture` or `publishedDeparture`; the operational `departureDate` is never used as the schedule. Exactly one row must pass `radarResultDecision`.
- **No generic timestamp as gate update.** Flex reports field-change deltas in `flightStatusUpdates` (for example `DGT`, departure gate) with the time Cirium recorded the change; a delta is not a physical observation of the gate. This routing does not use deltas: receipt is recorded as `receivedAt` with `observedAt: null` and `coverageState: provided_no_source_freshness`, and `gateUpdate` is always `null` for both providers. In the app the gate stays provider-reported.
- **Authorization.** Account, roster revision and published occurrence are re-admitted around each source and again **after the budget reservation, immediately before the paid call**. A revocation while waiting for the ledger stops the call; that reservation stays spent and the refusal is neither cached nor shared with coalesced requests.
- **Budget.** Each paid provider (`cirium-flex`, `flightaware`) has its own budget `RADAR_PAID_MONTHLY_BUDGET_USD` (default and maximum US$ 10; a higher value disables the provider). Costs per call (`CIRIUM_FLEX_COST_PER_CALL_USD`, `FLIGHTAWARE_COST_PER_CALL_USD`) are plain decimals converted exactly, without floating point: costs round up and the cap rounds down to the micro-dollar (`0.0050000000005` reserves 5001 micro-USD; a cap of `9.9999999999995` allows 9999999). Other formats (exponent, comma, more than 64 decimals) disable the provider. Spend is reserved in MySQL (`crewcheck_telegram_state`, key `radar-paid-spend:v2:{provider}`, per-UTC-day buckets) under a row lock **before** every upstream call, shared by all workers, and never refunded: failures, timeouts and abandoned attempts count. Because the providers' billing cycle and time zone are not confirmed, the cap is enforced over every rolling window of 33 UTC days: any calendar month in any time zone fits in such a window, so no billing month can exceed the cap. Without a ledger, a verified cost or remaining budget there is no paid call.
- **Cache and duplicates.** Answers are cached per provider and occurrence (5 min when usable, 2 min otherwise) and concurrent identical queries share one upstream call. Cached copies keep their original receipt, so the 30-min freshness checks still apply; the race no longer replaces receipt with `Date.now()`.
- **Activation.** Only with `CIRIUM_FLEX_RADAR_ENABLED` exactly `true`. When it is set but `CIRIUM_APP_ID`/`CIRIUM_APP_KEY` or the ledger runtime are missing, every query is refused (no Cirium, no FlightAware) instead of falling back to the unbudgeted legacy race. With the flag unset, `defaultCiriumRadarOptions()` stays `undefined` and the legacy race is unchanged. The AeroDataBox occurrence/health fix is a separate open PR (#1172) and is **not** incorporated here; this change does not touch `providerAeroDataBox`.

Validation: `scripts/regression-radar-paid-sequence.mjs` (three timezones, raw and prepared) covers the Flex adapter and appendix binding, Cirium-first sequencing, re-admission after reservation, refusal when incomplete, cost/cap rounding, the rolling window with a locking fake, cache/coalescing and the actual `runRadarRace` wiring. `scripts/regression-radar-paid-ledger-mysql.mjs` runs the ledger on a disposable real InnoDB (CI job `isolated-sql`, socket only): 120 concurrent attempts from three pools reserve exactly 40 under the cap, spend survives a pool restart, providers are separate, month boundaries never reset and the 33-day window frees spend only after 33 UTC days. No credential, paid query or network.

Open before activation: the per-call cost of the Flex Commercial Plan and of AeroAPI `/flights/{ident}` must be confirmed from the accounts; the ledger is a usage guard computed from those costs, not a provider-enforced spending stop (fixed fees and taxes are outside it). The cache and coalescing are per process; cross-process duplicates are bounded by the shared ledger. The real Flex envelope on the purchased plan is still unverified.

This change reuses the existing Cirium injection/transport and FlightAware adapter. It does not activate either account, change credentials, enable a paid query, change the current legacy provider race, or make a diagnostic endpoint operational. `CIRIUM_SKY_PRODUCTION_ENABLED=false` and registration stays disabled. Only a code-injected Cirium capability with `flightAwareFallback:true` exercises the new sequence. The existing disabled production factory prepares that option for a separately reviewed activation.

For the authorized published flight/date/route/exact planned UTC, await Cirium first. A usable departure gate with matching occurrence/provenance and a source observation within15minutes is sufficient: no FlightAware call. A failed/unavailable/timed-out primary, invalid occurrence, absent/placeholder/position gate or unknown/stale gate observation allows at most one existing FlightAware call after primary completion. The existing transport owns its bounded timeout and abort; the sequencer adds no overlapping deadline, retries or speculative calls. Context and host admission are revalidated around each awaited source and before starting the fallback.

FlightAware selects a unique response-owned exact occurrence rather than the first unfinished flight. Departure gate/terminal fields stay separate from arrival. Ambiguous/mismatched rows fail closed. The existing adapter has no documented per-gate source update time: provenance explicitly says source freshness unknown and separately records response receipt. Receipt does not become gate-change time and this path does not emit the manual-review gateUpdate proof. Cirium's observation clock likewise does not prove when a gate changed. Providers' fields are not blended: a useful primary status may be retained with no gate if fallback has no confirmed gate; no-data remains explicit.

The sequential path is read-only. The actual host rechecks linked account authority, active roster source/revision and exact published occurrence before returning, then returns before any canonical/Concierge writer. Revocation while waiting stops fallback or suppresses the final result. Production OFF behavior and existing cache/transport limits remain unchanged.
