# Operational weather timing regression

On a synthetic 12 October clock, the existing Home hook published CGH attention for a synthetic 20 October flight. Its selected next flight was valid, but its current METAR assessment was not related to that flight's operational window. No real roster, coordinates, provider call or notification was used in the reproduction.

This patch is separate from UI draft936, based on main88183e93. It keeps nextRealFlight and aircraft/weather severity thresholds unchanged. It extends the existing pure weather policy rather than implementing another monitor or classifier.

Both Home monitors use canonical absolute departure/arrival instants, with published leg clocks required so canonical fallback midnight does not create evidence. The server's existing origin policy is departure−180min through departure+30min; destination is arrival−120min through arrival+45min. Bounds remain inclusive. The shared policy is applied on every periodic check and again after an asynchronous weather response; cleanup or same-id canonical revision revokes pending responses.

The existing observation validator now has a reusable entrypoint: approved provider/provenance, matching ICAO and raw observation group, no future observations, and the existing ≤60-minute freshness policy. This is an application freshness policy, not a new aviation minimum or a forecast-validity rule. The API exposes actual per-report availability/official flags instead of treating successful TAF as successful METAR. Cache hits are usable only while the observation passes validation. Legacy raw-only landing cache cannot prove observation time/source and stays silent; no parallel cache or inferred timestamp is introduced.

Severity continues to come only from aviationReportMetrics(metar.raw). TAF-only updates no longer republish unchanged METAR attention. Manual weather consultation remains available for future-flight airports; its text explicitly distinguishes observation and forecast validity and does not claim coverage of that future flight date. No TAF forecast evaluator is introduced. Official format reference: https://aviationweather.gov/help/data/ (METAR observation time versus TAF explicit UTC validity period).

Synthetic tests run raw and canonically prepared hooks in UTC, America/Sao_Paulo and Pacific/Auckland, plus the actual compiled Home/Pulse and manual WeatherView under mocked API responses. Tests cover distant flight, exact opening/closing boundaries, expiration during response/JSON parsing, stale/future/mismatched/unverified reports, TAF-only success, cache hits, opt-out, cleanup, same-id clock correction, year rollover/APZ distinction, missing/invalid clocks, repeated observations and unknown provenance. Existing server critical-weather and heartbeat gates are preserved.

The fix controls publication; it does not clear previous Pulse session messages or alter queue, renderer, device permissions, notification consent/cooldown, server registration, credentials, migration or Play. Browser tests block every external origin and mock notifications/provider data. UI936 remains intact; integrating this patch with936/1023 later requires resolving only the Home changes and revalidating the resulting base/diff/CI. Draft/HOLD until independent review; publication remains behind Play/login.

Independent review of03180b9d found the published-clock guard incorrectly rejected canonical-supported `02:00(+1)` and `02:00 (+1)`. A regression uses the actual canonical constructor for an overnight20→21October leg, verifies identical departure02Z/arrival05Z for all three forms, positive origin at01Z, destination at03Z and no requests after05:45Z. The guard now accepts these specific supported suffixes while still rejecting missing/invalid clocks. The original031 checkpoint is not an approved candidate.
